##0. Executive Summary**What is real and differentiated.** The operating point in `configs/operating.yml` (stage3_tcn_prod.pt @ threshold0.5, trailing-realized-vol gate ≥2bps,10s cooldown) delivers crash recall0.38–1.0 across6 held-out days, F1 up to0.75, and zero calm-day alerts — and it is reproducibly measurably *better* than price-based alerting: it fires at crash onset with measured median lead times of7–30s, something TradingView/Cryptohopper/3Commas structurally cannot claim. The correlation-breakdown module (LUNA-vs-BTC:43 alerts ~5.9h before trough,0 on a calm day) is a validated second signal family nobody in crypto alerting sells. The anti-spam gate (zeros normal-day alerts) is a genuinely sellable guarantee.

**What is broken and must be fixed first.** The headline numbers rest on a **research-correctness cluster** that the verify critic confirmed is the dominant structural finding and the least cross-referenced: (1) crash labels use tick-count lookahead (`windows.py:72` `lookahead_ms //100`) assuming10 ticks/s while real tick rates are8–42/s — so "2% drop in5s" is actually ~1.2–1.8s on crash days and ~6.5s on the normal day (**RSR-02**, single highest-leverage finding); (2) `label_crashes` chain-splits one descent into507–718 overlapping "crashes", making recall denominators slice-dependent by up to56x (**RSR-03**); (3) offline backtests feed raw un-normalized features while the online path rolling-z normalizes, so offline→online threshold transfer is invalid (**BUG-03**); (4) four backtest evaluators use different TP/FP matching conventions (**RSR-04**); (5) the replay exporter attaches a200-tick-future score to the current tick, inflating every demonstrated lead time by ~5–7s (**RSR-01**). **Until these are fixed, no trust artifact (STR-01/04/11), golden test (TST-21), or replay export (NEW-05) should ship** — they would cement wrong numbers. Also unverified: whether any held-out crash day leaked into the training set (GAP-01), and the "0 alerts per100k" denominator is not machine-computed and is tick-rate-dependent (GAP-02).

**Critical reliability/security (equal priority to the research fixes):** crash alerts persist **only when a browser tab is open and forwarding socket events** — with no dashboard open, an alert exists only in one `console.log` line (**MLOPS-01**, the core watchdog failure mode). Sessions are forgeable on any deploy that doesn't set a real secret (`SESSION_SECRET` missing, public dev fallback — **SEC-01**) and have no expiry/revocation (**SEC-02**). The Caddyfile is an arbitrary-port open proxy to localhost (**SEC-03**). The replay service has a path-traversal local-file read (**SEC-04**). The inference sidecar reports `ready=true, score=0.0` for ticks50→199 and stamps heuristic scores as "tcn" (**BUG-04/BUG-11**).

**Main re-rank vs. the raw lenses:** the Rust proxy cluster (BUG-01/02) is **downgraded from P0/Critical to P1** — nothing consumes its output (`--source` is parsed but never read), the real ingest is the Node mini-service, so it is a dead-but-misleading subsystem, not a critical path. Conversely, **MLOPS-01 is elevated to P0** (browser-mediated alert loss), and the research-correctness items are elevated into the P0 set.

**Sequencing principle:** fix the labeler, lookahead, normalization, and matching protocol (RSR-02/03, BUG-03, RSR-04, RSR-15) → then the security/reliability P0 set (parallel, independent) → then productize the *corrected* numbers (STR-01/02) and the two validated signal families (STR-03, STR-05). Do NOT scale breadth (STR-09) before per-asset operating cards are automated (STR-04→RSR-15).

#### RSR-02 — Crash labels use tick-count lookahead, not wall-clock (CRITICAL, P0)
- **Description:** `ml/flash_crash_watchdog/data/windows.py:72` and `scripts/extract_windows.py:98` compute `lookahead_ticks = lookahead_ms //100` (assumes100ms/tick). Measured mean tick spacing: BTC-051923.7ms (42/s), LUNA-051032.7ms, ETH-080536.7ms, BTC-0116129ms (8/s). So the "2% drop in next5s" label is actually **~1.2–1.8s on crash days and ~6.5s on the normal day**. Every model trained on these windows (prod, v2, magnitude) learned a ~1–2s-horizon crash definition on crash days and a different horizon on normal days — a ~5x inconsistency in the label definition across the training set.
- **Repro:** `python -c "import pandas as pd,numpy as np; df=pd.read_parquet('data/parquet/BTCUSDT_2021-05-19.parquet'); print(np.diff(df.timestamp_ms).mean())"` → ~23.7ms; then note `5000//100 =50` ticks ≈1.19s, not5s.
- **Expected:** Labels defined in wall-clock ms (scan the mid series by timestamp, as `label_crashes` already does), with tick lookahead derived from actual timestamps.
- **Actual:** Hardcoded100ms/tick assumption; label horizon drifts per day.
- **Severity: Critical · Priority: P0 · Effort:1–2d · Deps:** none · **Timeline: Week1.**
- **Impact:** This is the single highest-leverage finding; every published recall/F1 number inherits it. Gate for STR-01/02/04/11 and TST-21.
