## 0. Executive Summary

**What is real and operating.** The shipped detector is a **single score-led alert** per event: Binance WS → 17 mid-price features → TCN sidecar (`stage3_tcn_prod.pt`, CUDA, SHA-256 pinned via `models/manifest.json`) → alert when `score > 0.5` **and** 25-tick trailing-vol ≥ 2bps **and** 10s since last alert → outbox (fsync'd JSONL) → socket.io :3003 → browser POST → Prisma/SQLite, with Telegram/Slack/PagerDuty/webhook delivery. Replay :3004, health :3005, web :3000. Live deployment is `START-WINDOWS.ps1` + winsw services. Verified healthy on 2026-08-13: sidecar serves prod model on CUDA, `/health` 200, `/version` reports `threshold 0.5 / gate 2.0bps / cooldown 10s`.

**Corrected validation (the numbers to quote now):** crash recall **0.27–0.74**, F1 **0.29–0.52**, **zero** calm-day alerts — per `configs/operating.yml`, which explicitly records the superseded chain-split + sweep-on-eval-day origin of the old inflated `0.38–1.0 / 0.75` claims.

**The alert-path fixes shipped this week (validated):** two-tier pre-alert + gated crash removed → single alert; trailing-vol gate reinstated on a **25-tick (~1–2s)** window so it confirms crash onset without lagging; 23 spam rows (vol < 2bps) purged from the outbox; `alerts.delivered.json` holds the 15 legitimate alerts.

**The dominant structural finding (audit-confirmed):** the **silent-degradation cluster** — a degraded-but-alive sidecar is converted to `score 0` while reporting healthy (✓ MLOPS-01 / LIVE-01), and the two headline differentiators are unobservable in the product: live lead time is always `ttdMs:null` (✓ STR-01) and correlation/de-pegging alerts reach no delivery channel (✓ STR-03). Fixing these three is the highest-leverage work in the project.

**Second-order cluster (audit-confirmed):** the container path is dead — compose cannot build (✓ ARCH-01), the containerized sidecar can never load the operating model (✓ ARCH-02), and there is no Prisma schema init so a fresh deploy has no tables (✓ ARCH-03). Web testing is effectively zero (✓ TST-04) and the live Telegram notifier + outbox durability are untested (✓ TST-02/03).

**Security posture is the weakest layer.** Unauth exposed sidecar `/score`+`/reset` (CVSS 8.8), live secrets in a `.env` already committed to the public Hugging Face Hub repo (CVSS 8.6), and a second process squatting on 0.0.0.0:8000 that produces 404s when the sidecar is down (see Appendix A).

**Sequencing principle:** Day-1 fixes (all sub-hour) → harden the live path (fallback, correlation delivery, TTD measurement) → make CI real → only then touch containers. Do NOT scale breadth (multi-symbol, 5-stage fiction) before the anchor path is instrumented end-to-end.

## 2. Project Analysis & Strategic Opportunities

### 2.1 What this actually is (honest baseline)
A **single-symbol (BTCUSDT) flash-crash detector** that is live and alerting today: one TCN-scored alert gated on a short trailing-vol floor, durable via outbox + dual persistence, delivered to Telegram and friends. Corrected validation: recall 0.27–0.74, F1 0.29–0.52, zero calm-day alerts. That's the real product. The containerization, multi-stage cascade marketing, and multi-symbol breadth in the docs are not the real product.

### 2.2 The genuinely differentiated levers (ranked)
1. **Pre-crash lead time — real only in the lab today (✓ STR-01).** Every live alert hardcodes `ttdMs:null`; the "warns before dislocation" claim is backtest-only. A forward-trough tracker (≥2%-in-60s after an alert → stamp `ttdMs`; timeout → close as non-event) converts the headline from marketing into an observable, saleable metric and unlocks live precision tracking. **This is the single highest-leverage change in the project.**
2. **The de-pegging/correlation signal — validated, unique, and currently undeliverable (✓ STR-03).** LUNA decoupling: 43 alerts ~5.9h before trough, 0 on a calm day — "nobody in crypto alerting sells this." But correlation alerts exist only in `console.log` + socket emit; a closed browser tab loses them. Routing through outbox + `notifyChannels` (~4h) makes the most distinctive demo a real always-on product.
3. **The anti-spam gate is the trust story — lead with it.** Score + vol floor + cooldown delivered 0 calm-day alerts after the 25-tick fix and the 23-row purge. "Zero false alarms on flat days" is honest and defensible — *once the inflated numbers stop being published* (✓ DOC-01).
4. **Distribution: an authenticated webhook contract for trading-bot integration.** The strongest near-term growth path. Today the webhook channel is undocumented, unauth'd, and treats non-2xx as success — unbuildable by an outside consumer.

### 2.3 What is NOT an opportunity right now
- **Containerization** — aspirational and broken (✓ A-01/02/03); the real deploy is `START-WINDOWS.ps1`, and compose would serve a stale model. Don't invest before the live path is instrumented.
- **Resurrecting the "5-stage cascade / 20 features" fiction** — the alert story got *better* by simplifying; the marketing that claims more is a liability.
- **Multi-symbol breadth** — non-anchor symbols already get heuristic-only detection with no honest label; breadth before durability is noise.

## 3. Issues & Required Fixes

### 3a. Correctness bugs
- **✓ A-07 (MLOPS-01) — Degraded-but-alive sidecar silently mutes the detector.** `index.ts:298-302` accepts only `source==='tcn' && ready`; a healthy-but-degraded 200 (`source='fallback'`, valid heuristic score) is converted to `score 0`. Since the fetch succeeded, `tcnFailureCount` never trips, `tcnAvailable` stays true, and the stream's own heuristic (catch-block-only) never engages. **Fix:** on `source==='fallback'`, use `data.score` or route to the local heuristic, and surface a degradation signal. *(1.5h.)*
- **✓ A-16 (LIVE-01) — fallback/warmup → score 0 while `tcnAvailable` stays true.** Same mechanism, filtered to the warmup/fallback responses. *(1h.)*
- **✓ A-17 (FE-01) — every alert renders twice.** Socket ids (`alert_<ms>`) can never equal Prisma cuids, so the `Dashboard.tsx:62` merge dedup is a no-op. *(0.5h — dedup on `dedupKey` or `createdAt+symbol`.)*
- **✓ A-15 (DATA-01) — replay artifacts mislabeled.** `eth-0805.json` / `lu-0510.json` say `BTCUSDT` while holding ETH/LUNA data. *(0.5h — re-run the exporter.)*
- **A-21 — delivery non-2xx = success.** Telegram/Slack/PD/webhook `fetch()` fulfills on HTTP 400/401; a bad `chat_id`/token drops alerts with **zero log output**. *(1h — check `res.ok`.)*
- **A-40 — throttled ticks mislabel source** (`source='tcn'` on heuristic scores) after entering fallback. *(1.5h.)*
- **A-46 — `catch (e) {}` swallows exceptions** across the live detection+alert path. *(0.5h.)*

### 3b. Performance & metrics
- **A-43 — tick emit + gate serialize behind the sidecar round-trip** (`index.ts:391`); a slow sidecar stalls ~1-in-5 ticks up to 2s (observed live: sidecar p50 ~10–100ms but a tail >1s). *(2h — score on latest cached result, don't block the emit.)*
- **A-48 — replay pipeline** ~120 events/s → 3 recharts re-render ~60fps. *(3h — batch + throttle.)*
- **A-08 (STR-01) — the metrics gap:** live lead time never measured (see §3 / §5). *(16h.)*
- **A-32 — no TCN-degradation observability.** The A-07 failure mode is invisible to every metric/channel. *(4h.)*
- Low-effort cleanups: A-55/57/58/59/60/64 (see table).

## Appendix A — Live incident 2026-08-13: sidecar `/score` HTTP 404 + connection failures

**Symptom (stream console):**
```
[tcn] Python sidecar URL: http://127.0.0.1:8000/score
[tcn] Failure #1: HTTP 404
[tcn] Unavailable after 3 failures - falling back to heuristic for 30s
[tcn] Failure #1: This operation was aborted
[tcn] Unavailable after 4/5/6 failures ...
[tcn] Retrying Python sidecar...
```

**Diagnosis (verified):**
- **Two processes bound to port 8000 simultaneously:**
  - `127.0.0.1:8000` → **PID 36108** — the real FastAPI sidecar (`uvicorn server:app --port 8000 --reload`, Python 3.12). Probed live: `/health` 200 `model_loaded:true` on CUDA, `/score` 422 (route exists; requires a body — **not** a 404), `/version` 200.
  - `0.0.0.0:8000` → **PID 42952** — `C:\Python314\python.exe app/run_all.py --demo`, an **unrelated process from another project**, started 15:59 (the sidecar came up 16:01).
- **Mechanism:** on Windows, loopback connections to `127.0.0.1:8000` prefer the specific `127.0.0.1` binding (the sidecar) while it's up. When the sidecar is **down or mid-`--reload` restart**, the only listener left is the demo's `0.0.0.0` wildcard, which answers `/score` with **404**; the reload gap produces connection **aborts**. The stream then spends 30s in heuristic fallback per retry cycle.
- **Confirmation of recovery:** sidecar `tcn_score_requests_total` climbed 560 → 567 in 4s, i.e., the stream is scoring again once the sidecar is up.

**Fix / prevent:**
1. **Stop PID 42952** (the `app/run_all.py --demo` squatter) — it is not part of this project, it hijacks 8000 whenever the sidecar is down, and its `0.0.0.0` binding exposes it to the network. (Confirm before killing — it may be a process you're using elsewhere.)
2. **Run the sidecar without `--reload` in the live setup** (the winsw service already does) so editing files doesn't drop the port under the stream's 500ms polling. Dev-mode reload flaps are the source of the aborts.
3. **Make the sidecar healthcheck visible** — a `source != 'tcn'` counter + staleness heartbeat reaching Telegram (ties to A-32), so "scoring on the wrong thing" is never silent (ties to A-07/A-12).
4. **Bind 127.0.0.1 explicitly** and verify with `netstat -ano | findstr :8000` that only the sidecar owns the port before starting the stream.
